# 社保、公积金业务判断与诊断

本次按业务上下文、诊断建议、结果核验、规则与经验四项接入现有 Harness。未调用申报网厅或真实执行器验证业务；集成测试使用本地模拟服务。

## 工作台入口

流程右侧「会话与工具」新增：

- **业务上下文**：查看任务、任务参数、应用参数的字段来源；填写本次业务预期。预期按申报账户绑定，不修改 DSL、任务数据或登录账户。来源差异仍会显示。修改预期后，旧核验结果失效。
- **诊断与对账**：查看执行提示、下一项核验、建议、缺少的核验项及逐人结果。
- **导入地区规则**：选择业务维护者准备的 JSON 规则文件，按编号合并到当前登录用户的加密知识库。导入前校验范围、日期、来源和重复编号。
- **归档已验证经验**：仅归档当前账户、当前流程版本、完整执行且业务 VERIFIED 的结果；还须包含官方状态或逐人对账断言。待处理、未知结果、单步执行不能归档为办结案例。

## 1. 上下文与变量溯源

Agent 使用 `get_business_context` 读取地区、申报系统、业务类型、主体、账户、所属期、人数、金额的候选来源。冲突不自动合并，流程名推断只作线索。缺少地区、系统、业务类型时，规则检索明确返回缺口。

`trace_flow_variable` 定向检索应用参数和嵌套步骤中的变量字段、表达式、子流程调用传参；传 flowCode 时沿用实际调用范围校验。结果按位置分页，保留禁用标识，不把静态出现位置当作实际赋值顺序。运行值及页面实际主体仍须结合已有执行证据确认。

## 2. 诊断建议

`get_diagnosis` 按错误证据给出账户主体、人工、待处理、数据、页面、环境等排查线索；分类不证明根因。相同错误重复两次时，提示先取得新证据。旧账户、旧版本证据会明确标识。

`record_diagnosis` 保留假设、证据编号、具体流程/步骤/字段、修改前后、理由、证据缺口及下一项验证。材料会进入后续上下文和预算结束时的结论；账户、版本、DSL 或最新执行证据变化后不再当作当前诊断展示。Agent 不能把自己的假设标为已证实。

扫码、验证码、UKey 应交还人工并保留原执行编号；审核中和银行处理中应查询原记录，不机械重放提交。这些判断还需现场核验，未新增自动处理验证码或自动轮询扣款的功能。

## 3. 结果核验

所有核验仍依赖当前执行新鲜、唯一、完整的最终页面。Agent 无权修改断言，用户在「业务断言」配置。新增：

- `textEquals`：精确核对企业、账户、所属期，避免子串误匹配。
- `businessState`：用户明确提供 `acceptedValues`、`pendingValues`、`failedValues`，分别表示办结、待处理、失败。未识别状态为 UNKNOWN，各状态集合不得重叠。
- `recordSet`：按人员行逐一核对唯一标识和结果；返回每人的预期、实际、核验状态及汇总。缺人、标识重复、字段提取不唯一为 UNKNOWN；额外人员或明确不一致为 FAILED。

缴费、汇缴、补缴场景必须覆盖账户、所属期、人数、金额、官方结果，缺项为 UNKNOWN。字段断言通过 `businessField` 指定用途，预期值必须与业务上下文一致；来源冲突须先核对。上下文不会自动生成页面定位或覆盖用户断言。若同时配置完整批次人员表和人数，预期记录数必须一致。

示例仅描述配置格式，选择器和状态必须依据实际网厅确认：

```json
[
  {"id":"account","type":"textEquals","businessField":"account","selector":"#account","expected":"示例账户"},
  {"id":"period","type":"textEquals","businessField":"period","selector":"#period","expected":"2026-11"},
  {"id":"count","type":"numberEquals","businessField":"personCount","selector":"#count","expected":2},
  {"id":"amount","type":"numberEquals","businessField":"amount","selector":"#amount","expected":100},
  {"id":"state","type":"businessState","selector":"#state","acceptedValues":["示例办结状态"],"pendingValues":["示例处理中状态"],"failedValues":["示例失败状态"]},
  {"id":"people","type":"recordSet","selector":"#results tbody tr","keySelector":".person-key","valueSelector":".result","pendingValues":["示例处理中状态"],"records":[{"key":"人员唯一标识A","value":"示例办结状态"},{"key":"人员唯一标识B","value":"示例办结状态"}]}
]
```

表格须覆盖完整目标批次。分页数据尚未采全会保留 UNKNOWN，不能仅核对当前页就宣布整批成功。人员标识须唯一；不同业务可采用人员与所属期等组成的明确标识。页面必须实际包含该标识，不能由模型猜造。

## 4. 地区规则与经验

没有内置未经核实的地方办理规则。规则由业务维护者根据实际依据导入，地区、申报系统和业务类型必须与上下文字面匹配；支持用户确认的名称或代码，不做模糊跨地区套用。

导入格式为数组，以下为格式示例，不是实际业务规定：

```json
[
  {
    "id":"example-region-system-payment-v1",
    "title":"示例规则，请替换为已核实内容",
    "region":"示例地区",
    "system":"示例申报系统",
    "businessType":"示例业务类型",
    "source":"请填写实际规则来源及版本",
    "effectiveFrom":"2026-01-01",
    "effectiveTo":"2026-12-31",
    "verifiedAt":"2026-11-06",
    "preconditions":["请填写有依据的前置条件"],
    "successCriteria":["请填写官方办结判据"],
    "rejectionAdvice":[{"reason":"示例退回原因","action":"经确认的处理办法"}]
  }
]
```

`search_business_rules` 仅返回适用且在有效期内、验证日期不在未来的规则，并保留来源。规则只提供参考，不改变工具权限或自行产生流程修改。

`search_experience` 返回 `references`（未验证流程范本）和 `cases`（已验证业务结果案例）。案例保留执行证据、版本指纹、核验详情、诊断假设及历史失败尝试。有效检索期为90天；适用规则或同一流程内容变化后，标记 `needsRevalidation` 并降低排序。验证过的业务结果不等于诊断原因已被证明，也不保证新任务可直接复用。

## 验证范围

单元测试覆盖来源冲突、账户绑定、变量嵌套、旧证据、状态映射、核验覆盖、人员重复/缺失/额外记录、规则日期和案例准入。Electron 集成测试覆盖实际表单、IPC、惰性 DOM 提取、待处理到办结、规则导入、加密经验归档与 MCP 检索。执行包加载采用主流程副本，避免加载子流程后污染主流程指纹。
